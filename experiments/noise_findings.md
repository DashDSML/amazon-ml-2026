# Noise analysis findings (NonStandard T18)

Hand-written analysis from `experiments/noise_analysis.md` (2026-09-25), which is
regenerated by `notebooks/noise_analysis.py` and holds only the auto-generated
tables. Keep this file separate so re-running that script never clobbers these
notes. Section numbers below refer to the tables in `noise_analysis.md`. Rates
are per matched pair unless stated otherwise.

**S1 is the clean, canonical side (§9).** S1 names are never upper-case, lower-case, non-Latin or accented, and have almost no junk characters or double spaces. S1 addresses are always present, and every S1 record carries a state (US: 2-letter code; India: full name). So S2/S3 noise is always measured *relative to a clean S1*. Normalisation should map S2/S3 toward the S1 form.

**Names**
- **Most names are close but not identical.** Only 6–14% match S1 exactly after case-folding. The median token_set_ratio is 100 (US) and about 92 (India). India's low tail (name_tsr_p05 ≈ 10) comes from names written in native script: 24% of S2 India names and 13% of S3 India names are in Devanagari, Telugu, Tamil, Kannada, Bengali, Gujarati, Gurmukhi, Malayalam or Oriya (§6). Blocking needs a retriever that doesn't depend on the name.
- **Gibberish replacement names** ("Xylodrex", "Caloumbra", "M/s Lyraavihalo") make up about 2% of US pairs and 2–4% of India pairs. These pairs can only be matched on address.
- **Both fields rarely fail together.** Pairs where both name and address token_set_ratio are below 60 (or the address is missing) are ≤1%. Almost every true match can be found through name *or* address, so fuse a name retriever and an address retriever.
- **Legal suffixes are the largest single token-noise source.** S1 has a legal form in 84% of India names and 54% of US names. It is dropped in 18–33% of matches and changed in 22% of India matches (Pvt Ltd ↔ Private Limited, Limited → Ltd) but only 2% of US matches. It is added in 7–9% of US matches and moved to the front ("LLC Moncada …") in 3–4%. Often the suffix is *replaced* by a generic word: private→center/services, llc/inc→com. Compare core names with legal forms stripped (T15), and keep suffix agreement as a weak feature only.
- **Tokens are added to names.** India matches gain honorifics (M/s, Sri, Shri, Smt, Dr, Mr). US matches gain "the", "dba", "formerly", "doing business as" and "www". Both gain generic words (Center, Services, Group, Trust, Holdings), a domain form ("bigsons.com", "DENTBIKESHOP.COM": 4–6% of pairs) and glued tokens (meerut kutir → meerutkutir). Asymmetric containment (T11) and a de-spaced char view are needed.
- **Typos.** About 10% of pairs have at least one name typo (2.7–2.9% of S1 name tokens). By distance: 1 edit 54%, 2 edits 31%, 3 edits 14%. By operation: replacement about 45% (about 8% keyboard-adjacent), insertion 22%, deletion 17%, adjacent transposition about 8%. There are also digit-for-letter swaps (8ureau, inc0rporated) and heavier scrambles (private→ptiave, 4% of pairs). Char n-grams handle all of these; word-exact blocking would not.
- **Other surface noise** (share of pairs):
  - accent injected into English text ("Léarning"): 5–7%. Accent folding is mandatory, which also helps France.
  - brackets around suffixes ("[Private]", "(Limited)"): 5–7%
  - junk prefix/suffix ("#", "@", "--", "***", "...", ">>", trailing "," or "&"): 4–10%
  - double spaces: 11%
  - duplicated token ("ALLIED ALLIED"): 3–5%
  - word order changed: 7%
  - case: S2 upper-cases 16–24% of names; S3 mostly keeps title case.
  - `&` → "and" or "+": rare (<0.5%)

**Addresses**
- **No postcodes anywhere in train** (0% in S1 and matches, §7). Postcode blocking and postcode features have nothing to learn from on US/India. Whether French records carry postcodes can't be checked under G1, so any postcode logic must be optional and default to "absent".
- **State.**
  - The state is almost never missing (<1%). Its form depends on source and country:
    - S2 keeps S1's form: US code 94%, India full name 72%.
    - S3 flips it: US code → full name (89%, e.g. TX → Texas), India full name → code (63%, e.g. Maharashtra → MH).
  - In 21–23% of India matches the state is written in native script (महाराष्ट्र, ಕರ್ನಾಟಕ, తెలంగాణ …).
  - Old names or states occur (Orissa → OD, Telangana → Andhra Pradesh, Bombay/Mumbai, Howrah/Kolkata), with the state actually changed in about 1%.
  - Map state code, full name and native script to one canonical key (a hand-written dictionary from general knowledge). With country, it is a safe coarse block.
- **City.** The S1 city appears as its own component in 57–80% of matches, as a variant in 3–8% (e.g. "Houston Township", "Baton Rouge City", "Brookpark"), and is dropped in 9–29%. S2 India drops it most often (29%). The US gets suffixes added: city, township, twp, county, cdp.
- **House number** (first number of the S1 address):
  - exact 73–79%; zero-padded 3–4% (537 → 0537); one digit edited 4–6% (709 → 708, 25677 → 2567, 149141 → 14914)
  - US: dropped 7–8% or otherwise changed about 4%
  - India matches add markers: "H.no", "Door No", "No", "#", "##", "Plot", "Block"
  - So a number *mismatch* is not a hard negative: about 10% of true pairs differ by one digit or padding. Features should separate exact, zero-pad, one-edit and conflict (T13).
- **Components are reordered** in 17–27% of US and 42–45% of India matches, e.g. state moved to the front. Compare addresses as token or component bags, not in sequence.
- **Street types are abbreviated** (street→st, road→rd, drive→dr, avenue→ave, lane→ln, court→ct, circle→cir, place→pl, boulevard→blvd) in about 45–48% of US pairs. Ordinals are spelled out (8th → eighth), US S2 addresses are upper-cased (89%), "Unit/Apt/Fl" parts are dropped, and "PO Box"/"PMB" parts are added. The mined table is in `noise_substitutions.csv`; use it for normalisation.
- **Missing values.** The address is missing in 4–5% of matches, and a literal `<NULL>`/`null`/`N/A` component appears in 3–4%. Treat these as missing, not as tokens.
- **Landmarks** appear only in India: 13% of S1 addresses have "near/opp/nr/behind/opposite/beside/next to", and 2–5% of matches drop them. None were found in the US.

**S2 vs S3.**
- S2 upper-cases more (addresses and names), uses more native script (India), keeps S1's state form, and drops components (India S2: city missing 29%, one fewer component in 45%). Its addresses are never identical to S1's.
- S3 keeps title case, flips the state form (code ↔ full name), reorders more in India, drops more components in India (2–3 fewer in 23%), adds house-number markers, and copies S1's address exactly in about 4% of pairs.
- Name noise is statistically the same in both sources.
- Source is a useful interaction feature for address comparisons.

**Distractors (§9, §10). They are near-copies of real S1 businesses, not unrelated records.**
- Nearest-S1 TF-IDF cosine: median 0.65–0.68 for distractors vs 0.76–0.82 for true matches' nearest S1. The distributions overlap heavily (distractor p90 0.83–0.87 vs match p50 0.76–0.82).
- 42–51% of distractors have a nearest S1 with name *and* address token_set_ratio ≥80 ("near_copy"). Only 6–13% are unrelated to every S1.
- The examples show the pattern: same street and nearby house number (76 vs 72 Orange Street; 80320 vs 80311 Elkview Ln), the S1 name plus extra words ("Diamond Medical Innovations Group Trust", "Heartland Society VI Group"), or a changed legal form. In other words, fake sibling businesses. This is exactly the chain/branch trap, and it means **number conflicts and extra name tokens are the main evidence against a match**. The model needs the T13 number features and T11 containment, and hard negatives must come from these near-copies.
- A distractor's nearest S1 is a singleton 8% of the time vs the 5.6% base rate. So distractors are not mainly "hidden matches of singletons"; they sit near every kind of S1.
- Surface differences are usable features:
  - distractors almost never lack an address (0.2–0.6% vs 4–6% for matches)
  - they rarely use domain-style names (0.6% vs 4–6%)
  - their names are longer (+4–5 chars, +0.6 tokens) because words are added
  - they have a legal suffix more often in India (63–72% vs 54–62%)
  - they have less junk prefix/suffix and fewer lower-case names
- Name/address/script noise otherwise looks like the matched records' noise (upper-case S2 addresses, native script, accents), so the same generator perturbs them.
- A plain char-3-gram TF-IDF top-1 (common trigrams pruned) already finds the true S1 for 87% (India) and 94% (US) of matched records. This is a useful blocking baseline.

**Implications, in priority order**
1. Normalise toward S1 form, in this order:
   1. NFKC and accent folding
   2. strip junk, brackets and `<NULL>` tokens
   3. collapse dotted acronyms (L.L.C. → llc)
   4. expand or contract with the mined table
   5. canonicalise states: code, name and native script → one key
   6. strip leading zeros from numbers
   7. handle house-number markers: H.no / Door No / # / Plot
   8. treat components as a bag
2. Blocking: within country, fuse a name char-n-gram retriever with an address char-n-gram retriever. Each alone misses 5–28% of pairs whose field is noisy, but <1% fail both. Don't rely on postcodes. Native-script India names need the address path or a transliteration view.
3. Features that separate distractors: house-number relation (exact / zero-pad / one-edit / conflict), extra-token containment (T11), core-name equality after legal stripping, address missingness, domain-style flag, source × field interactions.
4. Hard negatives: the near-copy siblings (same street, close number, name plus extra words) are what the model must learn to reject.

**Caveats.**
- Dotted acronyms tokenise into letters, so "L.L.C." shows up as `llc → l` plus added `l`, `c`, and "P.C." as `p c → pc`.
- "M/s" splits into `m` + `s`, which also produces a few spurious abbreviations (mani → m).
- Multi-word state expansions (NY → New York) are counted as dropped + added rather than as expansions.
- The US postcode detector only looks for a 5-digit component after the first one.
- Every count comes from a 100k-pair sample, so rare classes (under about 20 occurrences) are noisy.
